# XayaUI_CombatEngine

Shown in the in-game addon list as **XayaUI Combat Auras**; the folder, files, and slash commands keep the name `XayaUI_CombatEngine`.

In-combat aura tracking for XayaUI. It is a folder of the core addon: `XayaUI.toc` loads these files, and there is no separate addon
(checked 2026-11-04: no `.toc` in this folder). The name `XayaUI_CombatEngine` survives only in this heading, slash commands and older notes.

## What is in here
- `AuraModel.lua`: timing model (cast-anchored duration estimates, learned durations).
- `AuraTracker.lua`: evidence ranking for aura state when the game hides auras in combat.
- `AuraSetup.lua`: the "Combat Tracking Setup" window. It never opens over the game by itself (Xaya, SD-53, her words: "first run ever open with settings; otherwise put a config button in the rules pane"): the very first time ever the settings window opens while no spec has a saved or skipped setup, it opens together with it (`ns.AuraSetup_WithSettings`, called by `XayaUI_Options/Options.lua`; the record `auraModel.settings.setupShown` keeps it to once); otherwise only the **Open Combat Tracking Setup** button opens it (the Rules tab, `XayaUI_Rules/Editor/RulesTree.lua`, and Settings > UI Options > Rule Creation). It closes when the settings window closes (`ns.AuraSetup_SettingsClosed`; V27, SD-28), and it is locked in combat (V26). Before round 6 it opened by itself 6 s after login and after a spec change.
- (`AuraIDProbe.lua`, the diagnostic probe `/xui debug probe ids`, moved to XayaUI Dev Assist on qa-installer-branch; it is not in this folder.)
- `AuraDisplay.lua`: draws every aura display through Blizzard's own secure aura container so time and stacks show in combat (since 0.4.0): buff rules in dynamic groups as one container per group, every other buff rule as a single slot on XayaUI's own icon, and "Target Debuff (yours)" rules outside dynamic groups as a single slot on the target / focus. Automatic, no tag and no switch. Takes a display only when it can show it faithfully (shown while the aura is up; load and talent settings are followed live); everything else stays with XayaUI and `/xuiengine` names it with the reason. Positions come from XayaUI's own frames and layout rule (tests/layout_parity_run.py checks it). No speed guard (Xaya, SD-52, her answer: "Remove it (Recommended)"): the engine does not read the game's CPU meter, and nothing hands displays back or stops the engine because of a reading (before round 6, a "performance guard" did both: lean mode, then drawing off until /reload). Ships no spell data and never edits a rule. Needs XayaUI 0.5.93 or later. Design and risks: GitHub issues #280, #308, #310, #311. Bar cues (core 0.6.58, `XayaUI/BarCue.lua`): an aura-time or stacks Bar is drawn as a bar button (the game's duration bar or stack bar, icon, aura name, dispel-type coloring of the fill), in a single slot or as a member of a dynamic group; a cooldown / charges Bar stays with XayaUI.

## How it loads (since XayaUI 0.5.95 / engine 0.4.1)
- Since the platform split (XayaUI 0.6.76, P4) this folder is part of the addon `XayaUI_Rules` ("XayaUI Rules"): `XayaUI_Rules.toc` lists these files; the lines below that name `XayaUI.toc` describe the layout before that.
- XayaUI loads these files itself: `XayaUI.toc` lists them at the end. Cloning or pulling the repo into `Interface\AddOns\XayaUI` is all a player needs; no junction, no second folder.
- There is no separate `XayaUI_CombatEngine.toc` any more (an old copy installed as its own addon would step aside: the `ns.engineFiles` guard at the top of each file stops a second load).
- The engine cannot be switched off on its own (Xaya, SD-47, her words: "As long as there are any rules enabled that operate in combat, the engine must always run. It can only be turned off by disabling the rules that run in combat or disabling the rules addon"). It stops only when rules are switched off (`/xui disable`, which works in combat, until `/xui enable` or a /reload) or when XayaUI Rules is switched off in the AddOns list; a switched-off rule has no display, so the engine has nothing to draw for it. There is no switch in the settings window and no command: `/xuiengine` only shows the status. The old `/xuiengine auto off` and `/xuiengine off <group>` (a console command before core 0.6.56, then XayaUI Dev Assist only) saved an off state; that saved state is no longer read and is cleared at the first load of this version, with one chat line saying an old setting was removed (`AuraDisplay.lua` DB(); the speed guard's old notes guardV / guardUndone / guardTrips are cleared too, without a line).
- XayaUI's `Core.lua` publishes one deliberate global, `XayaUI_NS` (its namespace table). Each file here does `ns = XayaUI_NS or ns`, so `ns.AuraModel`, `ns.AuraTracker`, `ns.AuraSetup_Open`, `ns.IDProbe`, `ns.AuraDisplay` land in XayaUI's namespace.
- Saved data stays in XayaUI's `CueRulesDB` keys: auraTracker, auraModel, learnedAuraDur, idProbe, idProbeStream, setupShowError, setupBuildError, engineDisplay.
- Planned: narrow the whole-namespace bridge to a small `XayaUI_API`. Contract draft: project doc `claude/XAYAUI-COMBAT-ENGINE-SPLIT-CONTRACT-DRAFT-2026-11-02.md`.

## Ownership
The combat-engine Claude instance owns this folder. The core instance owns everything else, including `XayaUI.toc`, `Core.lua` and `Options.lua`. Changes to the bridge need both.
