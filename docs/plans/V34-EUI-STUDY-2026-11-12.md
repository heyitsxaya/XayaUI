# V34 and EllesmereUI: what EUI keeps unread when it is off (2026-11-12)

Requests: REQUEST-LOG A23 SD-56 (standing rule V34, her words: "if the addon or element within an addon is off it should not be
read at all. this is true for all addon elements and should be detected once per reload"), SD-57 (how V34 applies to the rule
editor and the right-drag tracker) and SD-58 (her V34 answers: buttons "what does EUI do?"; game-played aura sound and bar cues
"ask again later after we identify performance -- review EUI operation in the interim"; mover view only with the settings window
open; debug tools in one load-on-demand folder read only when Debugging is on).

Source studied: EllesmereUI public release v9.8.4, commit d83ffb7. An earlier study matched it by file size against her Drive copy
(docs/plans/AURA-CHECKS-EUI-STUDY-2026-11-12.md section 1). It was read as plain text with Read, Grep and Glob. Nothing in it was
run, loaded or written to, and her Google Drive was not touched.

Reference rule (Xaya, binding): the reference addons exist only to sanity-check our own work. This file records **behaviour only**:
what EUI does and which behaviour was checked. No EUI code, data, assets or text was copied into XayaUI, not even adapted, and EUI's
own button labels and messages are described, not quoted. Every design in sections 3 and 4 is our own, and our implementation is
independent of EUI's.

How to read the citations: a path with no prefix points into the EUI source tree (for example `EllesmereUI.lua:4337`). A path that
starts with **ours:** points into this repository. Markers: **UNVERIFIED IN GAME** = a claim about live game behaviour (a cloud
session has no game client). **INFERENCE** = reasoning, not read directly from a line. Everything else was read from the source and
then checked line by line by a second, adversarial pass. Where that check found a claim overstated or wrong, only the corrected
form appears below. Claims it could not support are listed in Appendix A.

## 1. Plain-language summary

**What the game allows.** WoW reads every file of every switched-on addon when you log in. The only way to leave code unread is to
put it in its own addon folder marked "load on demand" and load it only when needed. Code that has been read cannot be unloaded
until the next /reload.

**Buttons (minimap button, ESC menu buttons).** EUI keeps both in its main file, so their code is read at every login. It even
builds both buttons when they are switched off and simply keeps them hidden. Switching them on or off works at once, without a
reload. EUI does **not** meet V34 here. Our buttons are already stricter than EUI's: when they are saved off we build nothing and
listen to nothing. But our files are still read at login, so we do not meet V34 strictly either. Section 3 gives you four options.

**Whole modules.** EUI meets "off means not read" only for whole modules. Each module (bags, minimap, cooldowns and so on) is its
own addon. Turning one off in EUI's sidebar switches that addon off in the game's AddOns list and reloads the UI, so its files are
not read next session. That is detected once per reload, which is the shape V34 asks for. EUI uses "load on demand" only for its
settings window, its translations, and two unreleased modules.

**Aura sounds and timer bars.** EUI never uses the game-played aura sound that our rules can use. It plays every sound itself, from
hooks on Blizzard's Cooldown Viewer. Its timer bars are its own bars with a fast update loop that goes to sleep when nothing is
running. All of this code is read whenever EUI's Cooldown Manager is on, whether you set up any sound or bar or not. Some of it even
keeps running when nothing is set up. EUI is not a V34 model here. You asked to decide this later, so section 4 lists what to bring
back.

**Mover mode and debug tools.** EUI reads all of its mover (Unlock Mode) code at every login and runs most of it at every login,
because the same code places all frames. Its debug tools are not behind any player setting. Most are always read. EUI is not a V34
model here either. Your SD-58 answers already go further than EUI: the mover view only with the settings window open, and debug
tools in a folder read only when Debugging is on.

## 2. What EUI does, topic by topic

### 2.1 Buttons: minimap button, ESC game-menu buttons and other launchers

**What EUI does**

1. **Minimap button: where it lives.** It is a plain button on the minimap, made without any library, in the core file
   (`EllesmereUI.lua:3957`, `:3995-3998`). Left-click toggles the EUI window, right-click opens Unlock Mode, middle-click hides it
   (`EllesmereUI.lua:4031-4047`). In combat its clicks and drags do nothing (`EllesmereUI.lua:4032`, `:4052`). The core .toc lists
   the file and has no load-on-demand line, so the code is read whenever EUI's core is on (`EllesmereUI.toc:1-9`, `:49`).
2. **Minimap button: its setting.** It has one account-wide key, showMinimapButton. A missing key means shown, and only false hides
   it. A second key saves the drag angle (`EllesmereUI.lua:3967`, `:3973`, `:4082`; `EllesmereUI.toc:6`). The player hides it by
   middle-click or with a checkbox in a multi-choice dropdown on EUI's General options page. Both write the key and show or hide
   the button at once (`EllesmereUI.lua:4040-4046`, `:4092-4099`; `EllesmereUIOptions/EUI__General_Options.lua:1684-1690`,
   `:1721-1722`, `:1732-1734`).
3. **Minimap button: hidden still means built.** At login the core calls CreateMinimapButton with no condition
   (`EllesmereUI.lua:4113-4116`, `:4126`, `:4337-4338`). That function builds the whole button (textures, click, drag and tooltip
   scripts, position) and only checks the key at the very end, to hide it (`EllesmereUI.lua:3995-4086`). It also sets a global flag
   that nothing in the source reads (`EllesmereUI.lua:4088`). The key is read once at login for the starting state. After that,
   every change is applied live. There is no reload gate and no once-per-reload snapshot (`EllesmereUI.lua:4082-4099`).
4. **No library and no compartment entry.** EUI uses no LibDBIcon. LibDataBroker is listed but is only read by the DataBars module to
   show other addons' feeds (`EllesmereUI.toc:15-21`; `EllesmereUIDataBars/EllesmereUIDataBars.lua:3277`; `.pkgmeta:31-48`). No EUI
   .toc has an addon-compartment line, and no Lua file registers one. The core .toc has only an icon line for the AddOns list
   (`EllesmereUI.toc:7`).
5. **ESC menu buttons.** In the same login handler the core makes two buttons on the game menu: EllesmereUI_GameMenuButton (opens EUI)
   and EllesmereUI_UnlockMenuButton (toggles Unlock Mode). Both are always created, once, and placed by one hooksecurefunc on the
   game menu's Layout method (`EllesmereUI.lua:4340-4341`, `:4348`, `:4365`, `:4436`). In combat they print an error and do nothing
   (`EllesmereUI.lua:4351-4353`, `:4368-4370`).
6. **ESC menu buttons: their settings.** hideGameMenuButton shows the EUI button unless true. hideUnlockMenuButton shows the Unlock
   button only when explicitly false, so it is hidden by default (`EllesmereUI.lua:4458-4459`;
   `EllesmereUIOptions/EUI__General_Options.lua:1685-1688`, `:1717-1720`, `:1728-1731`).
7. **ESC menu buttons: hidden still means built and hooked.** Both buttons are built at login, and skinned then when EUI's Blizzard
   skin addon is loaded and its pause-menu reskin is on. The Layout hook stays installed. On every layout it first recolours the menu
   header (when the reskin is on), then reads both keys, hides what should be hidden, and returns early only when both are hidden.
   In combat it hides both and returns (`EllesmereUI.lua:4348-4433`, `:4436-4463`; header work `:4443-4455`, early return `:4463`).
8. **ESC menu buttons: timing.** The options setter only writes the key (`EllesmereUIOptions/EUI__General_Options.lua:1728-1731`). The
   buttons catch up on the next Layout call (`EllesmereUI.lua:4458-4463`). Whether Layout runs every time the menu opens is
   **UNVERIFIED IN GAME**: only a source comment says so (`EllesmereUI.lua:4443`).
9. **Read once at login.** Whether EUI's Blizzard skin addon is loaded, and its pause-menu reskin key, are read once to decide how
   the two ESC buttons look (`EllesmereUI.lua:4344-4346`). The menu reskin itself lives in that separate, not-on-demand addon and
   returns early when its key is off (`EllesmereUIBlizzardSkin/EllesmereUIBlizzardSkin.toc:15`;
   `EllesmereUIBlizzardSkin/EUI_BlizzardSkin_Dialogs.lua:351-361`).
10. **Settings window is load-on-demand, with more callers than "on open".** The page with these switches is in EllesmereUIOptions,
    which is load-on-demand (`EllesmereUIOptions/EllesmereUIOptions.toc:9`, `:32`). EnsureOptionsLoaded loads it
    (`EllesmereUI.lua:3316-3331`). That happens when the panel opens (`EllesmereUI.lua:3393`), on the first use of a module's slash
    command (`EllesmereUI.lua:3376`), in the first-install look picker (`EllesmereUI_FirstInstall.lua:497`) and in the style-choice
    popup (`EllesmereUI_StyleChoicePopup.lua:59`). Standalone builds bundle the options files and read them at startup
    (`EllesmereUI.lua:3317-3323`).
11. **Two more always-on launchers (checker additions).** The core registers an EllesmereUI page in the game's Options > AddOns list
    with an open button, using Settings.RegisterCanvasLayoutCategory and Settings.RegisterAddOnCategory, with no hide key
    (`EllesmereUI.lua:4819-4840`). It also registers its slash commands (/eui, /ee, /unlock and others) when the file runs
    (`EllesmereUI.lua:3714-3769`). Module slash commands start as small stand-ins that load the options addon on first use
    (`EllesmereUI.lua:3366-3381`). INFERENCE: the core commands exist whatever the button settings are.
12. **Minimap module: the game's addon compartment.** The separate EllesmereUIMinimap addon moves Blizzard's AddonCompartmentFrame onto
    its minimap or parks it on a hidden frame. It adds no entries to it. The key is hideAddonCompartment, default true, set by a
    toggle on the Minimap options page (`EllesmereUIMinimap/EUI_Minimap_Styles.lua:30-41`, `:95-139`;
    `EllesmereUIMinimap/EllesmereUIMinimap.lua:117`; `EllesmereUIMinimap/EllesmereUIMinimap.toc:9`;
    `EllesmereUIOptions/EUI_Minimap_Options.lua:1103-1110`). When hidden, the code still runs: the first call installs permanent
    hooks on the compartment, and every later apply re-reads the key. Apply runs at enable, after every loading screen, and live
    from the toggle (`EllesmereUIMinimap/EUI_Minimap_Styles.lua:105-126`; `EllesmereUIMinimap/EUI_Minimap_Lifecycle.lua:532-537`;
    `EllesmereUIMinimap/EUI_Minimap_Apply.lua:1236`). Its button flyout leaves the compartment and the expansion button out
    (`EllesmereUIMinimap/EUI_Minimap_Buttons.lua:191-203`).
13. **Minimap module: extra launcher buttons.** Great Vault, M+ portals, friends online and a flyout that gathers other addons' minimap
    buttons. Each has a hide key under hideExtraBtns, default shown. They are always built (Vault and portals are skipped only on
    the WoW Forever client). The setting only decides hide versus place-and-show on each layout pass
    (`EllesmereUIMinimap/EllesmereUIMinimap.lua:109`; `EllesmereUIMinimap/EUI_Minimap_Layout.lua:250-291`, `:789`, `:1236-1300`;
    `EllesmereUIMinimap/EUI_Minimap_Apply.lua:629-630`; `EllesmereUIMinimap/EUI_Minimap_Flyout.lua:534-613`). The flyout treats EUI's
    own minimap button like any other addon's, and on WoW Forever a new profile seeds it as ungrouped
    (`EllesmereUIMinimap/EUI_Minimap_Layout.lua:1367-1377`; LibDBIcon-button handling for other addons at
    `EllesmereUIMinimap/EUI_Minimap_Flyout.lua:137` and `EllesmereUIMinimap/EUI_Minimap_Buttons.lua:71`).
14. **The Minimap module itself can only be off as a whole addon.** Its apply step forces its own enabled flag on every time
    (`EllesmereUIMinimap/EUI_Minimap_Apply.lua:80-101`). A developer kill table exists, but it is empty and no setting reaches it
    (`EllesmereUIMinimap/EllesmereUIMinimap.lua:25`, checked at `EllesmereUIMinimap/EUI_Minimap_Apply.lua:81`). All ten of its runtime
    files are read at login whenever that addon is on (`EllesmereUIMinimap/EllesmereUIMinimap.toc:1-22`). The off switch is the
    module power button (section 2.2).
15. **The one counter-example.** The unreleased Simple Loot Council module has its own library-free minimap button, and it does not
    build the frame while its hide flag is set; it builds it the first time the button is shown
    (`EllesmereUISimpleLootCouncil/UI/MinimapButton.lua:215-224`). The whole addon is held back: load-on-demand that nothing loads,
    listed in EllesmereUI.HELD_BACK_ADDONS, and left out of the release package (`EllesmereUISimpleLootCouncil/EllesmereUISimpleLootCouncil.toc:13-15`,
    file listed at `:83`; `EllesmereUI.lua:861-864`; `.pkgmeta:63-64`).
16. **Client gate.** Line 1 of `EllesmereUI.lua` returns at once on a client blocked by `EllesmereUI_ClientGate.lua`, which the .toc loads
    first (`EllesmereUI.toc:12`). On such a client the file is opened but none of the button code runs.

**Markers**

- INFERENCE: EUI does not meet V34 for its minimap button or its ESC buttons. Both sit in the always-read core file, both are fully
  built at login whether hidden or not, the ESC Layout hook keeps running when both are hidden, and the settings apply live instead
  of once per reload (`EllesmereUI.lua:4337-4338`, `:4436-4463`). Only whole modules are truly unread when off.
- UNVERIFIED IN GAME: a hidden EUI minimap button probably costs almost nothing per frame, since its only OnUpdate is attached while
  dragging (`EllesmereUI.lua:4051-4065`). A hidden ESC button costs one hook call (plus header recolouring when reskinned) each time
  the menu lays out. Nothing in the source measures either.

**Implications for XayaUI (our side, read only)**

- ours: `XayaUI/XayaUI.toc:24-25` lists GameMenuButton.lua and MinimapButton.lua in the Platform (core), with no load-on-demand. So,
  like EUI, both files are read at every login.
- Minimap button, saved off: we make the saved table (ours: `XayaUI/MinimapButton.lua:34-39`) but no button frame and no event frame.
  The loading-screen listener exists only while the button is shown (ours: `XayaUI/MinimapButton.lua:277-287`). The button is built
  on the first refresh while shown (ours: `XayaUI/MinimapButton.lua:260-267`). That is stricter than EUI's build-then-hide.
- ESC button, saved off: no hook and no frame are made (ours: `XayaUI/GameMenuButton.lua:333-346`). Turned off after being on, the
  hook stays (the game cannot take a hook back) and returns at once (ours: `XayaUI/GameMenuButton.lua:305-319`). The change shows at
  the next menu open (ours: `XayaUI/GameMenuButton.lua:355-359`). Also stricter than EUI's always-built, always-hooked pair.
- Our always-on launchers match EUI's always-on ones: the game's Options > AddOns entry (ours: `XayaUI/Modules.lua:1310-1339`) and the
  addon compartment entry (ours: `XayaUI/XayaUI.toc:9`, `XayaUI/Modules.lua:1340`). EUI has the first and not the second. Neither has
  an off switch, so V34 has nothing to keep unread there (INFERENCE).
- The minimap button's quick-access list is also used by XayaUI Chat's sidebar, which can hold our button while the minimap button is
  off (ours: `XayaUI/MinimapButton.lua:19-21`, `:201-207`). Any split must keep that list available when the sidebar holds it.
- Both of our switches act live. V34 asks for once-per-reload detection, so a strict version must change that (section 3).

### 2.2 How EUI keeps whole modules unread (context for every V34 question)

**What EUI does**

1. **The split.** The suite is 25 addons: the core at the repository root plus 24 module folders, with 26 .toc files because Simple
   Loot Council ships two. The core .toc declares one account-wide SavedVariables, has no load-on-demand and no dependencies, and
   lists every core file, including the minimap button, the game-menu buttons, Party Mode, Unlock Mode, the friends kit and spec
   overrides (`EllesmereUI.toc:6`, `:49`, `:73`, `:76`, `:95`, `:106`).
2. **Modules are ordinary addons.** ActionBars, AuraBuffReminders, Bags, BlizzardSkin, Chat, CooldownManager, DamageMeters, DataBars,
   Minimap, Nameplates, QoL, QuestTracker, Quickdraw, RaidFrames, ResourceBars and UnitFrames each depend on the core, have their
   own SavedVariables and are not load-on-demand (for example `EllesmereUIActionBars/EllesmereUIActionBars.toc:8-9`,
   `EllesmereUIMinimap/EllesmereUIMinimap.toc:8-9`, `EllesmereUIChat/EllesmereUIChat.toc:8-10`,
   `EllesmereUIBlizzardSkin/EllesmereUIBlizzardSkin.toc:8-9`, `EllesmereUIBags/EllesmereUIBags.toc:9`).
3. **Client-type flags.** Some modules are limited to one game client by a .toc game-type line (for example
   `EllesmereUIFriends/EllesmereUIFriends.toc:2`, `EllesmereUIMythicTimer/EllesmereUIMythicTimer.toc:2`,
   `EllesmereUIGroupFinder/EllesmereUIGroupFinder.toc:2`, `EllesmereUIForeverEssentials/EllesmereUIForeverEssentials_Camelot.toc:2`;
   per-file tags in the core at `EllesmereUI.toc:20-21`). The same split is mirrored in Lua tables that drop wrong-client modules
   from the sidebar, groups and profile checklists (`EllesmereUI.lua:834-850`, `:877-886`).
4. **Load-on-demand is used for four addons in five .toc files:** the settings window (`EllesmereUIOptions/EllesmereUIOptions.toc:9`),
   translations (`EllesmereUILocales/EllesmereUILocales.toc:9`, per-file locale tags `:23-47`), Loadout Manager
   (`EllesmereUILoadoutManager/EllesmereUILoadoutManager.toc:12`) and Simple Loot Council
   (`EllesmereUISimpleLootCouncil/EllesmereUISimpleLootCouncil.toc:15`, `EllesmereUISimpleLootCouncil_Camelot.toc:16`). For the
   last two it is a hold switch that nothing loads, and the release package leaves both folders out (`.pkgmeta:8-29`, `:63-64`), so
   the hold only matters for tester or git installs. No .toc has an OptionalDeps line.
5. **What LoadAddOn is used for.** Only two calls load EUI's own addons: the settings window (`EllesmereUI.lua:3327`) and translations
   (`EllesmereUI_Locale.lua:228`, only when the effective locale is a supported non-English one, which includes a display-locale
   override on an English client, `EllesmereUI_Locale.lua:220-228`). The settings window is reached from many callers: panel open,
   slash stand-ins (installed while `EllesmereUI.lua` loads, not at login), the style picker, first install, the Bags bank-tab
   right-click (`EllesmereUIBags/EllesmereUIBags_Bank.lua:745-748`, called at `:3112`), DataBars block clicks
   (`EllesmereUIDataBars/Blocks/Currency.lua:232`, `Supplies.lua:366`, `LDB.lua:377`) and the friends colour picker
   (`EllesmereUI_FriendsList.lua:1377-1379`). INFERENCE: no combat check is visible on the bank-tab path
   (`EllesmereUIBags/EllesmereUIBags_Bank.lua:745-748`, `:3102-3112`). Other LoadAddOn calls load Blizzard's own on-demand UI
   (`EllesmereUI.lua:413-419`, `EllesmereUIMinimap/EUI_Minimap_Apply.lua:103-106`, `EllesmereUIActionBars/EUI_ActionBars_Init.lua:318-327`,
   `EllesmereUIQoL/EllesmereUIQoL.lua:1025-1035`, `EllesmereUI_AuraKit.lua:1603-1609`, `EllesmereUI_Panel.lua:4850-4859`). No path
   ever loads a feature module live.
6. **The module power button.** Each sidebar row has one, except rows flagged coming-soon, maintenance or always-loaded, and all rows in
   standalone builds. A click opens a confirm popup offering to disable (or enable) and reload. Confirming calls
   C_AddOns.DisableAddOn or EnableAddOn on the module's folder and reloads. The button reads the current state with IsAddOnLoaded.
   There is no live load or unload (`EllesmereUI_Panel.lua:1806-1859`). The reload is done first, inside the click, and the
   enable/disable call runs after (`EllesmereUI_Popups.lua:531-560`). Always-loaded rows that cannot be switched off include Party
   Mode (`EllesmereUI.lua:744`) and third-party plugin rows (`EllesmereUI_Panel.lua:5879`, `:6076`).
7. **Other enable/disable paths** follow the same set-then-reload pattern: first-install picker, profile pack import, a Cooldown
   Manager repair popup, uninstall, and Simple Loot Council turning off an older standalone copy (`EllesmereUI_FirstInstall.lua:106-122`,
   `:482-501`; `EllesmereUI_Profiles.lua:5219-5241`; `EllesmereUICooldownManager/EUI_CDM_Blizzard.lua:179-200`;
   `EllesmereUI_Uninstall.lua:794-797`; `EllesmereUISimpleLootCouncil/Edition.lua:51-77`). The core also turns Bags off on its own when
   a known bag addon is on, records that, and stops once the player has chosen (or re-enabled Bags after an auto-disable). It also
   turns off a stale old module folder, and Forever Essentials on other clients when a stale copy is enabled
   (`EllesmereUI_Startup.lua:466-495`, `:478-483`, `:507-510`, `:517-521`).
8. **Settings pages of off modules.** All module settings pages live in the one settings addon. When it loads it reads every module's
   page file, including those of off modules, and each returns at its top when the module did not load
   (`EllesmereUIOptions/EllesmereUIOptions.toc:42-118`, for example `EllesmereUIOptions/EUI_Minimap_Options.lua:7-9`; intent stated at
   `EllesmereUI.lua:3282-3287`). Held-back modules also return at the top of their runtime files, and translation files of modules
   that will not load return early (`EllesmereUILoadoutManager/EllesmereUILoadoutManager.lua:14-16`,
   `EllesmereUIGroupFinder/EllesmereUIGroupFinder.lua:8-10`, `EllesmereUISimpleLootCouncil/Edition.lua:8-12`,
   `EllesmereUI_Locale.lua:111-121`).
9. **Module start-up.** The first line of each module's first file is the client gate, and the module lifecycle runs its init at
   ADDON_LOADED and its enable at PLAYER_LOGIN (`EllesmereUI_Lite.lua:378-381`, `:491-521`; `EllesmereUI_ClientGate.lua:10-16`).
   Not every module uses that lifecycle or has the same header guards (Bags, BlizzardSkin, Chat, DamageMeters, QuestTracker and Simple
   Loot Council do not create themselves through it).
10. **When off modules are handled.** Only one step runs at login: the uninstall pass restores settings an off module left behind, at
    PLAYER_LOGIN or after combat (`EllesmereUI_Uninstall.lua:140-153`, `:385-396`, `:444-450`). Its account-wide restore runs only
    when the module is off for every character or missing (`EllesmereUI_Uninstall.lua:389-393`). The roster filter runs while
    `EllesmereUI.lua` loads (`EllesmereUI.lua:866-896`). Dimmed sidebar rows are drawn when the panel is shown (`EllesmereUI_Panel.lua:5258`,
    `:5481`, sync icon `:1889-1892`). The upgrade-track colour data is decided at file load (`EllesmereUI.lua:1839-1850`). Profile
    snapshots check whether a module loaded on export (`EllesmereUI_Profiles.lua:1059`, `:2292`).
11. **"Parsed but not run" (checker addition).** The core also defers running, though not reading. Unlock Mode's large body is stored as
    one function and run on its first use (`EUI_UnlockMode.lua:379-382`; `EllesmereUI.lua:3299-3312`), and settings pages queue work that
    runs only on first open (`EllesmereUI.lua:3272-3280`, `:3404-3409`). Standalone builds are a separate mode with no power button or
    sync icon (`EllesmereUI.lua:13`; `EllesmereUI_Panel.lua:1806-1808`, `:1866-1867`).
12. **In-module kill switches** that override the player's flag exist in Friends and Minimap (`EllesmereUIFriends/EllesmereUIFriends.lua:21-25`;
    `EllesmereUIMinimap/EllesmereUIMinimap.lua:25`). An older standalone Simple Loot Council makes the module inert, but its code is
    still read (`EllesmereUISimpleLootCouncil/Edition.lua:51-77`).

**Markers**

- INFERENCE: in practice EUI detects "module off" once per reload. The state is the game's own addon enable state, read at file load,
  ADDON_LOADED or PLAYER_LOGIN (`EllesmereUI.lua:1841-1850`, `EllesmereUI_Locale.lua:116-121`, `EllesmereUI_Uninstall.lua:129-153`,
  `EllesmereUI_Panel.lua:5325-5331`). The sidebar refresh, power-button hover and the CPU meter re-read the loaded flag during play
  (`EllesmereUI_Panel.lua:2299`), but never start or stop a module. The first-install picker reads the pending state for next session
  (`EllesmereUI_FirstInstall.lua:106-112`).
- INFERENCE: EUI meets V34 only at module level. Element switches inside the core or a loaded module are read every session and gated
  by settings. Whether "parsed but not run" (2.2 item 11) counts for V34 is her call.
- UNVERIFIED IN GAME: that a reload from addon code is allowed only inside a click, and that DisableAddOn takes effect next session,
  are source comments (`EllesmereUI_Popups.lua:531-541`, `EllesmereUI_Startup.lua:502-506`). That the client skips a disabled addon's
  files, and that IsAddOnLoadable is false for a load-on-demand addon, are client behaviour. Whether DisableAddOn without a character
  argument (`EllesmereUI_Panel.lua:1850-1854`, `EllesmereUI_Profiles.lua:5229-5232`, `EllesmereUI_FirstInstall.lua:116-121`) applies to
  all characters or the current one is unchecked; Simple Loot Council passes a character (`EllesmereUISimpleLootCouncil/Edition.lua:58`).

**Implications for XayaUI**

- Our split already matches EUI's module level: XayaUI Rules is its own addon that the player can switch off (ours:
  `XayaUI_Rules/XayaUI_Rules.toc:3`, `:7`), and XayaUI Options is load-on-demand and loaded with C_AddOns.LoadAddOn (ours:

## 3. Options for Xaya: the buttons ("what does EUI do?")

**What EUI does, in one line:** both buttons sit in EUI's always-read main file, both are built at every login even when switched off,
and switching them off only hides them, at once, without a reload. EUI does not meet V34 here.

**What we do today:** our two button files are read at every login, but when a button is saved off we build nothing and listen to
nothing; switching acts at once. Our addon-compartment entry and our entry in the game's Options > AddOns list are always on, with no
switch. All four options below are our own design.

**Option A. Keep the buttons where they are, as they are now.** Both files stay in XayaUI Platform. Saved off: nothing is built and
nothing listens, as today. Switching stays instant.
- Meets V34? No. About 700 lines are read at every login while off (ours: `XayaUI/MinimapButton.lua`, `XayaUI/GameMenuButton.lua`).
  You would be granting a written V34 exception for these two buttons.
- Cost: nothing new to build. Nothing runs while off (INFERENCE; UNVERIFIED IN GAME).
- **EUI's behaviour supports this option**, and EUI is looser still: it builds the buttons even when hidden.

**Option B. One small load-on-demand "launchers" addon holding both buttons.** XayaUI Platform reads the two switches once at login and
loads the folder only if either button is on, or if the chat sidebar holds our button (the sidebar uses the button's quick-access list).
Switching a button on during play loads the folder then. Switching both off hides them at once, and the files stay unread from the next
/reload.
- Meets V34? Yes, for both buttons together: off (both) means not read, detected once per reload.
- Cost: one more folder in the AddOns list, grouped under XayaUI. If only one button is on, the other button's file is read too (but
  not built).
- EUI does not do this.

**Option C. Two load-on-demand addons, one per button.** As option B, but the minimap button and the ESC button each get their own
folder, each loaded at login only if its own switch is on.
- Meets V34? Yes, per button, the strictest reading.
- Cost: two more folders in the AddOns list, and two load steps. The quick-access list must go with the minimap button and still load
  when the chat sidebar holds it.
- EUI does not do this.

**Option D. Keep only the always-on launchers.** Retire the optional minimap and ESC buttons, and open XayaUI from the addon compartment
(the game's minimap addons menu), the game's Options > AddOns entry, the chat sidebar and /xui. These have no off switch, so V34 has
nothing to keep unread there (INFERENCE).
- Meets V34? Yes, by removing the switches.
- Cost: you lose the minimap button's quick-access list, its icon and size choices, and the ESC menu shortcut. The chat sidebar would
  need its own list.
- EUI keeps an always-on Options > AddOns entry too, but it also keeps both buttons, so EUI only partly matches this.

INFERENCE (our recommendation is hers to make, not ours): if V34 is meant without exceptions, B is the smallest change that meets it.
If a small always-read file that does nothing while off is acceptable, A keeps things as they are and is already stricter than EUI.
