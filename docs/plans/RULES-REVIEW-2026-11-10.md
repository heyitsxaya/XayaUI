# Rules module review against Xaya's six criteria (2026-11-10)

REQUEST-LOG A23 SD-10. Scope: every file of XayaUI_Rules on main `ca2139a` (40 files, 27,043 lines, the merged rule editor included), plus core and Options where the keyboard lens needed them. Read-only review: no code was changed.

## How it was done

- 12 reviewers each read one slice of the module top to bottom against all six criteria; 4 more read the whole module through one lens each: runtime cost in a raid, game safety (taint, combat lockdown, secret values), keyboard / mouse / focus (the screenshot bug, SD-3), and the player's UX/UI.
- Every finding rated medium or above went to a separate skeptic told to refute it from the code and the API docs (default: refuted when the evidence does not hold). Findings rated low were not checked by a skeptic and are listed separately.
- Limits: no game client here. Costs and game behaviour are judged from the code, the API reference in docs/reference/api and runs in the test harness (standard Lua 5.1); claims marked INFERENCE are not documented. The skeptics refuted only 2 of 134 findings: the evidence they quote is real, but treat the severities as a first ranking, not a measurement.

### Decisions made along the way (process graph)

```
Review the Rules module (her request)
 ├─ Split by size into 12 slices of ~2,000-2,700 lines  → every line read once, no slice too big for one reader
 ├─ Add 4 whole-module lenses                           → slices miss problems that cross files (hot paths, taint, keys, UX)
 │    └─ keyboard lens covers core + Options too        → the screenshot bug can sit outside Rules (KeyCatch is in core)
 ├─ Skeptic per medium+ finding, default "refuted"      → stop plausible-but-wrong findings (2 refuted, 4 uncertain)
 │    └─ lows not verified                              → cost; they are cleanup, listed apart
 └─ Rank by the skeptic's severity, not the reviewer's  → the skeptic read the code a second time
```

## Totals

- 267 findings: 128 confirmed (critical 1, high 20, medium 95, low 12), 4 uncertain, 2 refuted, 133 low and not verified.
- Found twice by different reviewers (same problem, counted once when fixing): R14 and R15 (GameTooltip item comparison in the search list).
- Confirmed findings per criterion (a finding can touch several): 1 performance in the game: 51; 2 optimized structure: 46; 3 maintainable, clean, reliable: 51; 4 breaks other game functions: 20; 5 UX/UI: 73; 6 player's ability to play: 53.

## The screenshot bug (SD-3)

The keyboard lens found no XayaUI frame or text box that takes the keyboard at login while every XayaUI window is closed. The states it found that do hold PRINTSCREEN (and movement / keybinds) are, most likely first: (1) a key-taking window first set up in combat (the mover view from /xui unlock, the settings window, the version pane): keys are held until combat ends (critical, below); (2) a focused XayaUI text box that does not let go when combat starts (the report window, the copy box, the import window, the mover X / Y box); (3) the rule search box taking focus back about a quarter second after Esc; (4) the settings window's confirm popup in combat. If screenshots fail with every XayaUI window closed since login, the cause is probably outside these addons; in game, `/dump GetCurrentKeyBoardFocus()` and `/dump XayaUI_NS.KeyCatchList()` at the moment it fails would show it.

## Each reviewer's verdict per criterion

### slice:1

Scope: XayaUI_Rules/Visual.lua lines 1-1900 (art/texcoords, text formatters, group containers/anchors, dynamic layout, migration, group boxes, frame picker, X/Y popup, mover tags/handles).

1. Game performance: Per-display art and text helpers (ApplyCoords, CropTex, FmtRemaining, TimeFormatter cache) run only at config time or are already cheap. Two costs are real. The Auto group-box watcher polls at 5 Hz forever, in combat too: it calls SetBackdrop each tick and does a frame-by-folder scan using the linear FolderById. Each dynamic-group layout in combat walks every rule twice and allocates tables and closures. The mover view and the group picker re-measure every group every frame, which grows with the square of the folder count.

2. Optimized structure: Container() both gets and places the frame. Every call re-applies all settings and re-anchors the parent and followed groups, including from in-combat layout flushes and the combat engine's GroupFrame. GroupFitNeeded is not cached per pass (the outline is), so RefreshAllVisuals is O(rules^2) for fit groups. Polling is used where show/hide events already exist.

3. Maintainable and reliable: The file is a god-file that keeps group, anchor, picker and popup code next to the display art. Point tables are duplicated (FIT_PTS/PT_V/OPP/SIDE_OPP). ItemsExtent and MeasureOutline have already diverged (fit counts switched-off rules). pcall swallows box errors silently. Migration sets its done flag even when a group failed.

4. Breaks other game functionality: No Blizzard functions or tables are overwritten. Global names are prefixed, and the UISpecialFrames insert is the standard pattern. Secret values are guarded (issecretvalue in TimeLeftOf, ns.IsSecret on frame names). Two risks need in-game checks, both INFERENCE. First, group frames host Blizzard's secure AuraContainer and are re-anchored with no InCombatLockdown guard (LayoutDynamic, first show, tag/handle drags), which could raise ADDON_ACTION_BLOCKED. Second, the picker can anchor a group to its own XayaUIEngineN container, creating an anchor cycle.

5. UX/UI: A deleted group's border/background box stays on screen until /reload. The Auto-size box never shows around engine-drawn buff icons, i.e. in normal play. The Expiration sort is a snapshot. Clearing a group's strata or level has no effect until /reload. Invalid X/Y input is ignored without any message. Labels, tooltips and print messages are otherwise clear.

6. Player keeps control: Nothing here takes the keyboard. The edit boxes use KeyFocusGuard and Escape, the tag boxes and highlight take no mouse, and handles and tags appear only in the mover/unlock modes. The Shift-to-pick picker reacts to any Shift press for 30 s and stays open into combat. Mover-view per-frame cost can drop FPS on large setups.

### slice:2

### lens:ux

Scope: what the player sees and hears from the Rules module: displays, sounds and speech, chat output, and the editor.
(1) End-user performance: nothing in this lens costs frames while playing. Small items: Actions.lua compiles custom code again with loadstring on every run, and the dead VDH creator adds about 100 hidden widgets to each Auto-Generate page build.
(2) Optimized structure: the display paths share their styling (ns.StyleText is used by both Visual.lua and the combat engine's AuraDisplay.lua; BarCue decides bar colour and source once for both). The exceptions are the dead VDH code (RulesTree.lua:33-205) and the duplicate Select all controls.
(3) Maintainable and reliable: error reporting is uneven. Rule errors are reported once with raw Lua text and two different flags that are never cleared; custom-code errors are never deduplicated; step errors remember only the last message. Player-facing text still holds QA notes ('QA B33') and API names.
(4) Breaking other game functionality: no taint or key-eating found in this lens. The mover's arrow keys go through core KeyCatch and PRINTSCREEN is never held. The one outward risk is that Group, Say and Yell actions have no rate limit, so a fast-toggling rule can spam party or raid chat (server throttling is INFERENCE).
(5) UX/UI: the weakest area. The Combat Tracking Setup window opens on its own for every new spec with no 'don't ask again'. Mid-fight performance-guard messages are jargon. The rule Info tab is a raw ctx dump. The editor offers a 'Custom' cue that does nothing. 'aura', 'visual', 'display' and 'cue' are mixed in player text. Panel styles differ across frames (purple Arial Narrow setup window, orange popups, red-gold save bar). Bad numbers typed into boxes are dropped without a word. The game-played sound quietly moves to the Ambience channel.
(6) Player keeps control: the main risk is the 660x560 mouse-enabled setup window. It can open 6 s after login or a spec change and is not hidden when combat starts, so it can block clicks in the centre of the screen during a pull. The frame picker also picks on any Shift press and closes itself after 30 s without notice.
