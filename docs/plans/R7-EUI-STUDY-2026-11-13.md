# Round 7 follow-up: how EUI handles three things Xaya asked about (2026-11-13)

Her questions (REQUEST-LOG SD-67): gate fix "How does this get handled in EUI?"; 0.2 s re-checks "1 but sanity check against EUI"; replay allowance "How is this handled in EUI?".

Method: one reader per question over EllesmereUI's source (read as text only, behaviour only; nothing copied), then an adversarial checker re-opened every cited line. Below are the CHECKED results. Our implementation is independent. EUI paths are relative to the EUI source root; XayaUI paths to this repository.

## 1. Timers per event (gate failure)
- EUI's hot aura and cooldown paths do not make a timer or a closure per event. Three patterns: a pending flag plus one C_Timer.After with a named function (EUI_AuraBuffReminders_Refresh.lua:1514-1535; EUI_BlizzardSkin_HUD.lua:955-969; EUI_CDM_Events.lua:24-37, 268-273); a hidden frame whose OnUpdate hides itself, set off by :Show() (EllesmereUIQoL_MovementAlert.lua:1756-1779); a dirty flag plus an animation-group ticker that stops after 11 quiet fires, 11 x 0.1 = 1.1 s (EUI_CDM_HookViewers.lua:489-495).
- EUI is not free of per-event garbage: its bar-glow handler reads C_Spell.GetSpellCooldown for each tracked spell on every cooldown event, on purpose (EllesmereUICdmBarGlows.lua:364-372, 381-389, 419-422; the API returns a struct, namespaces.md:4400; new table per call is INFERENCE).
- EUI has no event-replay gate and no per-handler garbage test; its one memory test has no timers (.tools/tests/test_font_family.lua:294-307). It shows addon CPU from C_AddOnProfiler in its panel (EllesmereUI_Panel.lua:2285-2359).
- XayaUI already uses the first pattern: Kick arms at most one timer of each kind with named callbacks (XayaUI_Rules/Engine.lua:1421, 1427-1431, 1471, 1486, 1500-1515). The checker found one more timer the first reader missed: ArmWake calls C_Timer.NewTimer(delay, OnWake) after every pass and re-makes it when the earliest wake moves earlier (Engine.lua:1291-1308). Its callback is named; NewTimer returns an object (namespaces.md:4674). So a gate fix must cover NewTimer as well as After.
- Control (run 2026-11-13): moving only the gate's bookkeeping in tests/gate_common.py addTimer: UNIT_AURA allocating runs 294/1950 (15.1%) -> 2/1936 (0.10%); 294 x 1936 / (1950 x 2) = 145.9, about 146 times fewer. The 2 left are not yet explained.
- Unknown: whether the game's real C_Timer.After/NewTimer makes Lua garbage. Not in the reference. Needs an in-game /run test.

## 2. The two remaining 0.2 s re-checks
- Range (A): EUI uses the game's events where they exist and re-checks on a timer only where none covers the unit, only while the feature is on: crosshair 0.15 s, nameplates and target distance 0.2 s, boss frames 0.4 s, raid refiner 0.5 s. EUI has no spell-range check to focus, mouseover or pet, and leaves out its own pet's range on purpose (EUI_RaidFrames_PetFrames.lua:234-235). XayaUI's 0.2 s is inside EUI's 0.15-0.5 s. Difference: XayaUI keeps polling a loaded focus/mouseover/pet rule even when the unit does not exist (cheap early return, XayaUI_Rules/Triggers.lua:562). Focus and pet have start events (events.md:1177, :1616); mouseover has an appear event (:1679) but none for leaving.
- Hidden cooldown end (B): EUI also keeps a fallback re-check for running cooldowns ("eventless ready-edge belt", EUI_CDM_HookPresetCooldowns.lua:456-471), started by game events and at most once a second (EUI_CDM_HookViewers.lua:480-486). XayaUI's is 0.2 s, at most 1 / 0.2 = 5 a second, so up to 5 times more often. Worst case, a 120 s cooldown with no duration object: 120 / 0.2 = 600 re-checks. The "is it running" flag is NeverSecret (structures.md:6531, :6545), so either re-check can always see the end.

## 3. Countdown text and bar fill redraw (replay allowance a)
- EUI has no exact-parity test. On its aura bars the tenths text key and the written text use the same rounding, math.floor(remaining*10 + 0.5) and "%.1f" (EUI_CDM_BuffBarPresets.lua:418-434), so a redraw at the same moment shows the same text. Only EUI's cast bar keys on the floored tenth.
- XayaUI's effects loop keys on the floored tenth but writes the nearest tenth, while a full pass writes the nearest tenth with no key (Visual.lua:2314-2343, 2727-2731). For 4.80 to 4.85 s left the loop still shows "4.9" while a full pass writes "4.8". That is the text part of allowance a (INFERENCE from the code; needs a test run). Keying on the rounded tenth, as FmtRemaining already rounds, should remove it.
- The bar-fill part (0.01 for a frame) is timing, not rounding. EUI gives no exact-parity example for it: it eases buff fills and does not read back game-driven cooldown fills.
