## What was built
- `ns.Settings(module)` (XayaUI/Modules.lua section 0b, first in the file so everything loaded after it has it). Modules: platform,
  core (rule tracking), qol, chat, bonus, reskin, devassist. It returns a **view**: an empty table whose metatable reads and writes the
  module's keys in today's `CueRulesDB` (`ns.Settings("reskin").rsk` is `CueRulesDB.ui.rsk`, see the owner table). In P5 only the
  backing behind a view changes; the call sites stay.
- The views hold no data: every access looks up the current `CueRulesDB`, so a view kept in an upvalue since load survives anything
  that replaces `CueRulesDB` or one of its keys (the loader setting the saved variables, a profile import, Reset everything, a backup
  Load (replace), a whole new table). Reads never create anything; a write creates the key (and `CueRulesDB` itself if it does not
  exist, as the sites that wrote it did). `ns.SettingsReady()` replaces the old `type(CueRulesDB) == "table"` guards.
- The seven views are made once when Modules.lua loads: `ns.Settings(m)` for a module that is off creates nothing (V14; test D).
- Ownership: each view knows its module's keys. A key it does not own still reads and writes (nothing breaks in game) and is counted
  (`ns.SettingsUnknownKeys()`); `ns.SettingsStrict(true)` (tests) raises instead. Cross-module reads go through the owner's view:
  Bonus DataPanels reads Chat's `chat` through `ns.Settings("chat")`, Reskin BlizzardSkins reads QoL's `shoppingList` through
  `ns.Settings("qol")`, Visual / Drafts / Options read the Platform's `ui` through `ns.Settings("platform")`.
- Hot paths keep the table in an upvalue and look it up again only when `ns.settingsEpoch` changes (a number on ns): no metamethod per
  frame / aura read / tooltip. The epoch moves on a view write that changes a key (writing the same table back, `x = x or {}`, does
  not), on `ns.SettingsChanged()` (called by `ns.FireReady()` after the saved settings are set up, and after a db profile part is
  applied) and when `CueRulesDB` itself is a different table (seen on the next view access). Sites: AuraAlias `ns.AuraAliasesOf`
  (every aura read), Conditions learned durations / proc-glow counts / learned stacks, Timing stores, Combat/AuraModel and
  Combat/AuraTracker `DB()`, QoL CursorTrail and CursorHighlight OnUpdate, Bonus `TT.DB()` (every tooltip), Dev Assist DevRecord `Ui()`
  / `Rec()` (every recorded line). The invariant this needs: outside the Platform nothing writes `CueRulesDB` directly (the guard test
  enforces it); Platform writes of a module key happen only in Core.lua's saved-variable set-up (followed by FireReady) and in a db
  profile part's apply (followed by SettingsChanged).
- Measured (Lua 5.1 through lupa, this container, 5,000,000 reads; not the game client, so the numbers are relative): the old
  `CueRulesDB and CueRulesDB.cursorTrail` 28.6 ns, a view read 180 ns, the epoch-cached read 21.5 ns. So every hot path above is no
  slower than before; the remaining view reads are in settings pages, slash commands, set-up and walkthroughs (INFERENCE: not
  measurable in game; each adds about 0.15 µs per read).

4. **characterReskin:** written only by XayaUI_QoL/CharacterReskin.lua (QoL), filed under the "Blizzard Reskin" profile part. Kept as

7. **`ui` sub-keys other modules use** stay under the Platform's `ui` for now: ui.snapMode (Visual.lua, the mover), ui.auto

## Tests
New: `tests/settings_seam_run.py` (50 checks).
- G guard: no direct `CueRulesDB` (name, or the string "CueRulesDB" in rawget) outside the Platform allow-list; in Platform files no
  module key directly except in Core.lua / Modules.lua. Negative control on 2faeda5: fails with 319 uses.
- B byte-identical saved data: the harness's full play session (every command, minimap row, option) plus a /reload, fixed clock and
  addon versions, every addon on and core alone: sha256 of the canonical saved variables equals the old code's (GOLDEN made with
  `--golden` in a checkout of 2faeda5; run twice there, same hashes). Also no unknown key asked during the sessions (fails on 2faeda5:
  no seam). Note: "byte-identical" is the canonical JSON of the saved tables (key order sorted), not the game's file text order.
- C held views: first-run defaults, a QoL / Bonus / Blizzard Reskin profile part applied, Theme Reset everything, backup Load
  (replace) (bar group spacing back), CueRulesDB replaced as a whole and removed; hot-path cache (AuraAliasesOf) follows a view
  write, SettingsChanged and a part apply; `x = x or {}` does not move the epoch. Fails on 2faeda5 (no ns.Settings).
- D module off: core alone; every view, every key read: CueRulesDB, frames and event registrations unchanged; same view each call.
- E every view writes / reads exactly CueRulesDB.<key> (Reskin: ui.<key>); unknown module nil; unknown key counted / strict raises;
  only characterReskin owned twice.

Existing tests changed (setup only, no assertion changed): they load single files with a stand-in namespace, so they now also load
the real Modules.lua (the seam) first: aura_display, aura_sources, bar_cue, calculator (Modules.lua behind the stand-ins through
__index), charges_combat, class_learn, count_gcd, cursor_idle, cursor_trail_cost, devassist_probe, engine_garbage, layout_parity,
load_alloc, load_class, load_ids, perf, tracked_buff. Tests that poked `CueRulesDB.<key>` directly between steps (which no game code
does any more) now write through the view so the hot-path caches see it: aura_display (auraAlias), debug_record (debugRecord; and its
extracted Options.lua block gets the file's `CoreS, PlatS, QolS` locals), trigger_parity (learnedAuraStacks).
