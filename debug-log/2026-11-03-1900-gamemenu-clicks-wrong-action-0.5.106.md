# Xaya: Game Menu skin, a click runs the wrong action (XayaUI 0.5.106, fork: main)
Logged 2026-11-03 ~19:00 UTC. GitHub issue: #312 (continued). Xaya: "game menu reskin still breaks all button placement" (screenshot, skin on), and, asked which symptom: "clicks the wrong action". 0.5.96 (click-time lookup by text, click-swallowing cover) did not fix it.
Cause: not found by reading. The old design drew its own panel with its own sizes, then found the real button by its text and called :Click() on it. I could not reproduce a mismatch offline and could not fetch Blizzard's GameMenuFrame source, so the exact way a row reached another entry stays unknown (candidates: a text lookup that missed and fell back to a remembered pooled button that had been recycled into another entry; rows ordered by stale on-screen positions). Instead of one more patch on the lookup, the lookup is removed.
Change: new default mode "Match Blizzard's button positions". Each row is anchored to its real Blizzard button (top-left and bottom-right), the panel is exactly Blizzard's menu rectangle, and no row, no panel and no cover takes the mouse, so the click lands on the real button and runs its own action. Hover / pressed looks are read from the real button (polled every 0.03 s while the menu is up). The XayaUI row is the real slot GameMenu.lua adds after Macros (the skin draws it); buttons other addons added to the menu get a row too. Own-layout mode (old look, own sizes) stays as an option; there a click that finds no real button with the same text now clicks NOTHING (a remembered button counts only if it still has the same text) and prints a line in chat. /xui gamemenu shows the mode and each row's real button (layoutIndex, top, left). Also: the third-party addon name is removed from the comments in GameMenuSkin.lua and GameMenu.lua.
Verified offline: tests/gamemenu_run.py 25/25 (stand-in menu with a recycling pool and AddButton / InitButtons: rows anchored on the right buttons, no mouse, hover / pressed read from the real button, pool order change followed, an added third-party button drawn, no Click() sent in match mode; own layout: right entry clicked, nothing clicked when the text is gone or stale); load_class, timing, aura_display, layout_parity, import, skin_button suites; compile check of GameMenuSkin.lua, GameMenu.lua, Options.lua.
Unverified in game: everything above is a stand-in; in particular that the real menu's buttons keep taking clicks while the menu frame is at alpha 0, that anchoring rows to the pooled buttons lands exactly on them, where the title sits (it follows Blizzard's header), and how the polled hover looks. Not changed: the order and group gaps of the own-layout mode still come from on-screen positions.
Needed from Xaya / Insivius: open the menu and click each row; if a row still runs another entry, `/xui gamemenu` output with the menu open (it now prints the mode and each row's real button).
