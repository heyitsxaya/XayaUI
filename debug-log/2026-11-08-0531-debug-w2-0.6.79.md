## #461 product fix: "Style the fixed blue too" (her answer, 2026-11-07)
Reproduced (V3) in `tests/bar_cue_run.py` (real addons in the stand-in game): a Bar cue on an aura with no tooltip type and no dispel type,
Colour style Neon / Pastel / Muted: the drawn colour was 0.25 0.62 1.00 every time (her "the bar stayed the same blue"). The engine path
(Part B, the real Combat/AuraDisplay.lua) handed the game a `customDispelColorMap.None` of the plain blue in every style.
Cause: `ns.BarCueColor` returned `ns.BAR_FALLBACK_COLOR` as it is (BarCue.lua fallback), and `ns.BarDispelColorMap` set `None` (and any
dispel type the game gives no colour for) to the same unstyled blue.
Fix: `ns.BarFallbackColor(style)` = the fixed blue through `ns.BarStyleTransform(style, ...)`; used by the fallback of `BarCueColor`, the
engine map's `None`, and a dispel type with no game colour. Blizzard default and Custom keep the plain blue (her decision text: "Custom is
unchanged: it picks colors per type"; `BarStyleTransform` has no function for either). No game API involved (V2: none).
Values (the style formulas applied to 0.25 0.62 1.00, rounded): Neon 0.00 0.49 1.00, Pastel 0.66 0.83 1.00, Muted 0.39 0.54 0.70 (hue kept), Blizzard / Custom 0.25 0.62 1.00.
Tests (fail on 121502f, pass now): bar_cue_run.py "Neon / Pastel / Muted on the fixed blue" (A, drawn colour) and "B: <style>: the
engine's 'None' colour" (3 + 3 failed on the old code); parity checks of the engine fill colour against XayaUI's own bar.
V4 scope (`git grep BarCueColor / BarDispelColorMap / BAR_FALLBACK_COLOR / BarStyleTransform`):
- `BarCueColor`: BarCue.lua Paint (XayaUI's own bar), Combat/AuraDisplay.lua BarButtonInit (engine fill; map only when "fallback") and
  BarLookKey (colour is part of the look key, so a style change makes a new slot; also keyed by BarStyleSig), Rules_Options Editor.lua
  Colour "Now:" line swatch (follows), QAWalks-bars.lua steps 3 / 4.
- `BarDispelColorMap`: AuraDisplay.lua only.
- `BAR_FALLBACK_COLOR` left as is: the "Fixed color" mode's default before a pick (BarCue.lua, a chosen fixed colour, not the type
  fallback), the Custom pickers' default swatches (DisplayTab.lua, Editor.lua: Custom is unchanged).
Walkthrough: bars-cues step 4 now expects Neon to change the fixed blue (text and check: Blizzard default of a no-type bar is
`BarFallbackColor("blizzard")`); tests/qa_walks_bars_run.py step 4 with no type now Pass (was Fail by design in 0.7.53), with a
negative control (a style that changes nothing: Fail).

## #462 macro tooltips (built: the Macro part only)
Reproduced (V3) in tests/macro_tooltip_run.py (real addons): no post-call existed for `Enum.TooltipDataType.Macro`, so a macro's
"fire damage" line stayed as the game wrote it, with no Spell ID line (9 of 14 checks fail on 121502f).
API (V2), from `docs/reference/api/` (12.1.5):
- `Enum.TooltipDataType` … `Macro` = 25 (enums.md).
- `## C_Macro (3 functions, 3 documented)`: `C_Macro.GetMacroName(macroId: luaIndex)` → `name: cstring?` · SecretArguments=AllowedWhenUntainted;
  `C_Macro.GetSelectedMacroIcon(macroId: luaIndex)` → `textureNum: fileID` · SecretArguments=AllowedWhenUntainted;
  `C_Macro.RunMacroText(text: cstring, button: cstring)` · HasRestrictions, SecretArguments=AllowedWhenUntainted (namespaces.md).
- `C_ActionBar.IsMacroActionWithShowTooltip(actionID: luaIndex)` → `isMacroActionWithShowTooltip: bool` · RequiresValidActionSlot,
  SecretArguments=AllowedWhenUntainted (about action slots; not used).
- `GetMacroSpell` is NOT in the public reference (undocumented globals are left out of it) and not in Blizzard's generated documentation
  (the full 12.1.5.70688 dump in her Drive folder "Blizzard API Data" has no match). The TooltipData table's fields are not documented
  either: TooltipInfoSharedDocumentation.lua describes only `TooltipDataArg`.
- Blizzard's own UI: the reference does not include FrameXML, so how ActionButton builds a macro tooltip was not checked (not available).
INFERENCE (unverified in game, marked in the code): a Macro tooltip's `data.id` is the macro's index and `GetMacroSpell(index)` returns the
spell the macro shows (XayaUI_Rules/Conditions.lua reads it the same way).
Fix (Tooltips.lua section 1e, `TT.OnMacroData`, hooked in `TT.Init` only, so V14 holds: no hook while every tooltip feature is off):
1. Type colours run on the macro tooltip's own lines (they need only the text).
2. The spell is resolved and the same spell processing runs (`TT.OnIDData` with the Spell kind: Spell ID, aura lines, formulas), but only
   when `GetMacroSpell` exists, both values are readable numbers, and the spell's name equals the tooltip's first line. Otherwise
   nothing is guessed (colours only). `TT.lastMacro` keeps the macro ID, the spell ID or why none, and the coloured words (for the walkthrough).
Tests: macro_tooltip_run.py (colour drawn on the line, Spell ID line, no double colouring, parity Spell vs Macro tooltip, name mismatch,
no GetMacroSpell, secret ID, Type colours off). tests/options_bonus_off_costs_nothing_run.py and tests/feature_rows_map_run.py now expect 11 post-calls when on (was 10).
Waits: Chaos (A1), Physical (A2), other 3+-school names (A3); school colours unchanged.
V4 scope: `TT.ID_KINDS` readers (Init hooks, TooltipsUI options list) unchanged: no new setting row (a "Macro IDs" switch would be her choice);
`TT.OnIDData` gains an optional 4th argument (`colored`) used only by the macro path.
