## The change (Options 0.6.100, Skin.lua)
ScanDropdowns keeps the widths it measured (text -> width). They are valid for the measuring string's font: the key is its font file,
height, flags, text scale and effective scale (GetFont, GetTextScale, GetEffectiveScale, read once per scan); any change drops them
and every distinct text is measured again. The answer is the same widest text: the scan still walks the whole tree, only a text it
has measured is not measured again. A cap of 20,000 kept widths. ns.OptionsApi.WidthScan holds the last scan's counts (scans, texts,
measured, width) for the walkthrough and the test. Nothing else changed: DDMin (FlexPrepass) and the dropdown list's width
(pullout Open) still measure with TextW as before.
API facts (V2), docs/reference/api/widgets.md, FontString, quoted in full:
- `GetStringWidth()` → `width: uiUnit` · SecretWhenAnchoringSecret · SimpleFontStringAPI
- `GetFont()` → `name: cstring, fontHeight: uiUnit, flags: TBFFlags` · SimpleEditBoxAPI
- `GetTextScale()` → `textScale: number` · SimpleFontStringAPI
- `GetEffectiveScale()` → `effectiveScale: number` · SecretReturnsForAspect=[SecretAspect.Scale] · SimpleFrameAPI
The measuring string is XayaUI's own, anchored to UIParent: no secret anchoring. INFERENCE (undocumented): a text's width depends only
on the text, the font and the scale; the key holds all of them, so a change of any measures again (fails safe).
Scope (V4, git grep): TextW callers DDMin (Skin.lua FlexPrepass), ScanDropdowns, the dropdown pullout's Open; ScanDropdowns' only caller
ns.UpdateMinWidth (from ns.DecorateTrees); `of.xuiDD` written by UpdateMinWidth, cleared by its release restore and by RulesTree.lua
FillRule; `pf.xuiDD` in the pullout code is an unrelated flag. XayaUI_QoL CharacterToolkit's TextW is a different function.

## Found, not changed (for Xaya)
1. The sidebar refresh is the biggest part left (40-48% of the click's stand-in time, 59% of its game calls after this change). One
   click runs the tree's RefreshTree 5 times: twice on the released / not yet filled tree (ACD's CleanUserData SetTree(nil), then
   SetStatusTable before SetTree: AceGUI draws nothing, but TreePaint repaints the old rows and Skin's row fit re-runs on them), then
   SetTree, Select, and the next frame's FirstFrameUpdate. Skin.lua's row fit runs AceGUI's refresh up to 12 times per call and starts
   from the reused widget's remembered row count and size.
2. AceGUI hands back a pooled widget with `next(pool)` (AceGUI-3.0.lua newWidget), an order set by memory addresses, so which old
   tree / tab group a redraw gets, and the size the row fit starts from, changes with unrelated allocations. In the stand-in the same
   click painted from 145 to 5,273 sidebar rows depending only on that pick (this is why a first version of this measurement looked as
   if the width change slowed the sidebar: with the pick fixed, before and after are identical). INFERENCE: the same happens in the
   game, and may be part of why her two runs differ (136 vs 221 ms).
   Not changed: skipping the empty-tree refreshes or starting the fit from a fixed size changes where the fit starts, and so possibly
   how many rows the sidebar shows: a visible change that needs her answer (proposal in the report).
3. The whole options table is rebuilt on every click (16-18%). Rebuilding only the changed rule needs proof that no other part of the
   tree (lists by enabled / loaded, Smart Categories, group rows, search) reads what the click changed: not done here.
