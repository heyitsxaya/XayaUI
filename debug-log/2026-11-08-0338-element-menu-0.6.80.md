# Element menu: right-click an element while the settings window is shown (PS-59, #495) (XayaUI 0.6.80)

Logged 2026-11-08 03:38 UTC. Branch `claude/lucid-mayer-pv4ytn`, base origin/main 4ffb6e1 (conflicts / reload + patch notes). Not on main.
Versions: XayaUI 0.6.80, Rules 0.6.78, Options 0.6.92, Chat 0.6.44, QoL 0.7.51, Bonus 0.6.35, Dev Assist 0.7.61 (Rules Options, Reskin,
Nameplates, Media: no code change). QA step I3; walkthrough "element-menu", `XayaUI_DevAssist/QAWalks-element-menu.lua`.

Her words (PS-59, prescriptive): "Also with the options panel on, right clicking an element object should open up an at-cursor menu to
allow the user to select "element options" and modify position with x,y inputs"

## Built as stated
- Only while the settings window is shown; a right-click on an element opens a menu at the cursor (10 px right of / below it, as the
  #267 group popup does) with exactly an "Element options" button and "X" and "Y" input boxes. No title, no Apply / Close button. Enter
  (or Tab, or leaving the box) applies at once; Escape in a box puts the shown number back; Escape or a click outside closes the menu.
- An element whose existing right-click menu has entries keeps them: only the unlocked display (#61 menu). Its title (the display's
  name) stays on top, then Element options, X, Y, then every #61 entry in the same order (Snap Target >, Linked Auras (move together) >,
  Center Vertically, Center Horizontally, Paired Aura >, divider, Free Move (radio), Drag Snapping >, divider, Edit This Aura, Edit Its
  Group (<name>)). An entry with a sub-menu opens the game's own context menu (MenuUtil.CreateContextMenu, as #61 does) with that entry's
  choices. The #61 menu itself is built from the same list (Visual.lua VisualMenuParts) and is unchanged (parity test).

## The #495 proposals used (her words leave these open; not answered by her)
1. Elements = every XayaUI element with a settings page that registers (`ns.RegisterElement`, Modules.lua section 11): rule displays (all
   kinds, bars included), the data panels, Notepad, Calculator, Shopping List panel, chat sidebar, Chat Data Panel, and the Character

## How (Modules.lua section 11)
- `ns.RegisterElement{ key, label, targets(add), page | open, getPos, setPos, rows, mouse, blizzard }`, pcall-wrapped. Each module
  registers when it makes the element's frame (GetFrame, Build, BuildPanel, MakeSlot, the reskin's Hook): a module or feature that is
  off makes no frame and registers nothing (V14).
- XayaUI_Options calls `ns.ElementWindowShown(true)` from Tree.DriverStart (each draw while shown: new frames join) and `false` from
  Tree.Closed. While shown, each target's script (OnMouseUp, or OnClick for a button registered for right clicks) is replaced by a
  wrapper: a right-click opens the menu (and the old right-click does not run), any other click goes to the frame's own script. On close
  every frame whose script is still the wrapper gets its own script back; the sidebar strip's mouse is switched off again. While closed
  no wrapper is on any frame (test). The menu frame is made at the first menu (none in a session without one); GLOBAL_MOUSE_DOWN and
  PLAYER_REGEN_DISABLED are registered in its OnShow and unregistered in OnHide.
- Blizzard frame (Character window): a post-hook (HookScript), put on at the first opening out of combat; Blizzard's own handler always
  runs; the hook returns at once while the window is closed. The game has no way to remove a hook: it stays until /reload (V14 limit 2).
- Level of V14 reached: code in always-loaded addons (parse cost only); no frame, event, hook or handler until the window is shown and
  an element exists.

## API facts (V2), docs/reference/api (12.1.5)
- widgets.md: `SetPoint(...)` · CheckAllowInheritForbiddenLayoutAspects, IsProtectedFunction, SecretArguments=AllowedWhenUntainted;
  `ClearAllPoints()` · IsProtectedFunction; `EnableMouse(enable: bool = false)` · IsProtectedFunction, SecretArguments=NotAllowed;
  `IsProtected()` -> `isProtected: bool, isProtectedExplicitly: bool` · SecretReturnsForAspect=[SecretAspect.ObjectSecurity];
  `SetScript(scriptTypeName, script?)` and `HookScript(scriptTypeName, script, bindingType = "Extrinsic")` -> `success: bool` ·
  ChecksForbiddenAspects=[ScriptBindings], RequiresAssignableScript, SecretArguments=AllowedWhenUntainted;
  `IsMouseOver(...)` -> `isMouseOver: bool` · ConstSecretAccessor, SecretArguments=AllowedWhenUntainted, SecretWhenAnchoringSecret.
- events.md: `GLOBAL_MOUSE_DOWN (button: cstring) · SynchronousEvent · SystemInfo`; `PLAYER_REGEN_DISABLED · SynchronousEvent · Unit`.
- namespaces.md (C_RestrictedActions): "Documented but not present in this client: `InCombatLockdown`"; the global InCombatLockdown is
  what XayaUI already calls (Sidebar.lua, Share.lua, GameMenuButton.lua). INFERENCE: the global returns true in combat lockdown.
- Combat handling: a protected frame (IsProtected true, or the call fails) is never given a handler. In combat the menu does not open
  (the frame's own right-click runs), X / Y do not apply, and an open menu closes at PLAYER_REGEN_DISABLED. All registered frames are
  XayaUI's own plain frames except CharacterFrame (post-hook only, put on out of combat). INFERENCE: CharacterFrame is not protected;
  if it is, the check skips it.
- MenuUtil: no entry in docs/reference (Blizzard UI code); it is what #61 and the rules sidebar already use. The element menu's inputs
  are not put into a MenuUtil menu (no documented input element); the menu is XayaUI's own frame in the look of the #267 popup.
