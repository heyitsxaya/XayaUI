## 3. Causes
(a) The list jumps up.
- Old Sidebar.lua:1028 `local function SelectRoot() ns.GoHome() end` and Editor.lua:2191 `ns.GoHome(tab)`: every delete selects the
  list's top row (TreeHelpers.lua:280: Loaded, or All in Smart Categories). The window rebuild that follows
  (AceConfigDialog-3.0.lua:1751 `tree:SelectByValue(...)`) goes through AceGUI's TreeGroup:Select (AceGUIContainer-TreeGroup.lua:512-523),
  which calls `RefreshTree(true)`: scroll the selected row into view (:442-461). Loaded is the second line, so the list jumped to the top.
- "Still": the earlier fix is Skin.lua's Select wrapper (old Skin.lua:946-962: "Re-selecting the row that is already selected now keeps
  the sidebar exactly as the user left it ... a genuinely new selection still scrolls into view; a rebuild does not"). It does not hold
  for a delete: the selection changes (the deleted rule -> Loaded), and the wrapper is taken off on release (old Skin.lua:963
  `AddRest(w, "sel", ...)`) and only put back after the rebuild, so the rebuild's own Select is AceGUI's. (The eye button's fix in
  Sidebar.lua MakeToggle avoids a rebuild instead; a delete needs one.)
- Second cause, seen as a flaky stand-in result near the bottom of the list: Skin.lua's row fitting (old :987-1033) refreshes the tree
  several times with a pretend height. AceGUI clamps the scroll position to each pass's line count (TreeGroup.lua:436-438), so a first
  pass with too many lines pulled a list scrolled near its bottom up for good; and from AceGUI's 18 px first guess (a recycled tree
  widget has no remembered count) the 8 one-row shrink passes ran out on ~38 px rule rows, so the last pass still had too many lines
  and clamped the position (59 -> 40..50 in the stand-in).
(b) The bar stays.
- Old Sidebar.lua:1569 / 1571: `ns.MultiCount` / `ns.MultiHas` count the selection set (rule tables) whether or not the rule is still
  in the list; only the bar's Delete (N) (old :1699) and Move (N) (:1617) empty it. Right-click > Delete (`DeleteRule`, :1030), Del on the
  open rule (:1985), Delete this rule (Editor.lua:2186) and Delete Group and All Contents (:1067) never touched it, so Skin.lua:773 kept
  painting "Delete (3)"; Move (N) would have moved the deleted rule inside the Recycle Bin; a rule put back from the bin came back purple.

## 4. Fix
- TreeHelpers.lua `ns.GoHomeKeepScroll(tab)`: leaves the tree's scroll position on its status table (`xuiKeepScroll`, only when the
  delete stays in the same list), then `ns.GoHome`. Used by `SelectRoot` (all Sidebar.lua delete paths) and Editor.lua's Delete this rule.
- XayaUI_Options TreePaint.lua `KeepScroll`: right after a window rebuild (Options.lua's Open wrapper now calls
  `ns.DecorateTrees(nil, true)`), a tree carrying the mark gets its position back and the pending scroll-to-selection dropped; AceGUI's
  own clamp keeps a list that got shorter at its bottom. Only after a rebuild, so a decorate pass before it cannot spend the mark.
- Skin.lua's fitting passes: each pass starts from the scroll position asked for (a scroll-to-selection asked for is asked of every
  pass); a shrink step drops `floor((total - room) / tallest drawn row)` lines (at least 1). Each dropped row is at most that tall, so a
  step never goes below the largest count that fits: the result is the one the one-row steps reach, in fewer passes.
- Sidebar.lua multi-select: `Prune` drops every selected rule that is no longer in `ns.rules` (and the Shift+click start point);
  called by `ns.MultiCount`, `ns.MultiHas`, `ns.MultiMove`, `ns.MultiDelete`, and after every delete (`SelectRoot`, Editor.lua). Exported
  as `ns.MultiPrune`.
- RuleSettings.lua: `MultiHas` and `GoHomeKeepScroll` are published on `ns.OptionsApi.RuleEditor` for the walkthrough (Dev Assist
  may not use the rule editor's own names; the full suite's static check).
- Not changed: what the right-hand pane shows after a delete (still the list's top page), and right-click > Delete deletes only the
  right-clicked rule (a "Delete N Selected" entry is request row 23, a separate item).
