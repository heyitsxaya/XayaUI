## #476 "missing devourer" (built: the Devourer part only)
Reproduced (V3) in `tests/load_class_run.py` with a stand-in class API: `SpecChoicesAll` (Editor.lua) looped `for si = 1, 4` and stopped
at the first index the game answered with nothing, so a spec after a gap never showed, and a fourth index holding an "Initial" spec
would have been listed.

API (V2), quoted from `docs/reference/api/` (12.1.5):
- `C_SpecializationInfo.GetNumSpecializationsForClassID(classID: number)` → `specCount: number` · SecretArguments=AllowedWhenUntainted (namespaces.md)
- `GetSpecializationInfoForClassID(classID: number, index: luaIndex, gender: UnitSex?)` → `id: number, name: cstring, description: string, icon: fileID, role: cstring, recommended: bool, allowedForBoost: bool, masterySpell1: number?, masterySpell2: number?` · SecretArguments=AllowedWhenUntainted (globals.md)
- `C_SpecializationInfo.GetSpecIDs(specSetID: number)` → `specIDs: table<number>` takes a spec SET ID, not a class ID, so it is not a class's spec list (not used).
- The live 12.1.5 function list (`api.json` "live") has `GetNumSpecializationsForClassID` only under `C_SpecializationInfo` (no global) and
  `GetSpecializationInfoForClassID` only as a global (no `C_SpecializationInfo.GetSpecializationInfoForClassID`, which the old code tried first).
- Neither entry marks an "Initial" spec. Blizzard's client data (`docs/reference/content/classes.json`, build 12.1.5.70783) lists one per
  class (name "Initial", order 4): 1444, 1446-1456, 1465; Demon Hunter: Havoc 577 (order 0), Vengeance 581 (1), Devourer 1480 (2), Initial 1456 (4).
- Game Data Capture's all-class scan (in game, 2026-11-01, interface 120105; `docs/reference/spells/README.md`) used the same
  count-and-skip loop (`C_SpecializationInfo.GetNumSpecializationsForClassID` then `GetSpecializationInfoForClassID(classID, i)`, skipping
  nil) and found Devourer (1480), Havoc (577), Vengeance (581) and no Initial spec.

Fix: loop 1 to the game's count per class (1 to 4 when the count is not available), skip an empty index instead of stopping, skip the
Initial spec IDs above. INFERENCE: why index 3 came back empty for her is not known (the stand-in models a gap with Devourer at index 4).
The capture above is the evidence the new loop finds Devourer in game; the walkthrough's step 1 writes what the game answers for
`GetNumSpecializationsForClassID(12)` and each `GetSpecializationInfoForClassID(12, i)` into its note, so a miss is explained by data.
Waits: "specs should follow ticked classes" (A7 / A8; not built). Questions: none for Devourer (A9 only if this route fails in game).

## #484 part 2 "import button has wrong alignment" (built: the row only)
Reproduced (V3) in the stand-in window (real AceGUI): on Rules > Smart Categories > + New Rule every row's icon sat at the row's left edge
and its text 40 px in, but Import's icon was 8 px in, its text 62 px in and 20 px lower (centred in a 76 px row), as in her screenshot.
Cause: the skin's row function (Skin.lua SkinRow) moved the icon to +8 and the text to icon + 18 and floored each row at icon + 40 px;
for each row it then re-laid the list out (DoLayout), which put every EARLIER row back to AceGUI's own Label layout (icon at the left edge,
text 4 px after it). Only the last row, Import, kept the moved layout.
"Aligned" taken from the neighbouring rows (all nine rows above Import, the same widget: a full-width Label with a 36 x 36 icon): icon at
the row's left edge, text 4 px right of the icon, vertically centred text, the icon crop. Fix: the row skin no longer moves the icon or
text or floors the height; every row, Import included, keeps that layout. Measured after: Import and Dynamic Group both x +0 icon,
+40 text, same row x and width, at 1000 px and 700 px windows.
Waits: part 1 (the profile import mode, A11) and part 3 (done earlier).
V4 scope: `SkinRow` runs only for a Label whose option has `arg.xuiRow`; the only `xuiRow` option is the type picker's `Entry`
(RulesTree.lua:1112), so only the picker rows change. `xuiMinH` / the re-measure hook are referenced nowhere else (git grep).

## #487 the picker drawn over Drafts (built)
Reproduced (V3): + New Rule on Smart Categories, then Drafts: the picker's ten rows were drawn at the top of Drafts above the drafts
(inline boxes are not hidden by the page wrapper), and the picker stayed open after a sub-tab change or a closed window (`picker` was
cleared only by a pick or Cancel). Its rows were 76 px tall but stacked at their 36-39 px AceGUI height, so they overlapped.
Fix:
- the picker belongs to the sub-tab it was opened in (`picker.sub`); its rows and the page entries they replace look at the option path
  AceConfigDialog passes (info[2] = the sub-tab), so it is never drawn on another sub-tab;
- `ns.PickerSync` (run from `ns.SaveRulesSub`: every redraw, every 0.25 s while the window is open, and when it closes) forgets it once
  another Rules sub-tab is open or the window is closed; + New Rule now selects the sub-tab before the redraw;
- on Drafts (New Rule pressed there) the drafts' inline boxes hide while the picker is open, like the other pages' entries;
- row heights: see #484 (each row as tall as its icon or text, stacked at that height; no overlap at 1000 or 700 px).
V4 scope: `picker` is set by StartNewRule and cleared by PickType, Cancel and now PickerSync; read by the rows' and wrapped entries'
hidden functions in `all` (Smart Categories), `PickerInto` (Loaded, Disabled, Drafts) and the copies in each Smart Category (MakeSmart).
`ns.SaveRulesSub` is called from Options.lua Notify (:406), the window's OnRelease (:1517), Tree.Closed (:1616) and Tree.Tick (:1628).
`ns.UI.NewRule` is called only from the + New Rule button (Skin.lua) and StartNewRule from the group menus, both in the open window.
