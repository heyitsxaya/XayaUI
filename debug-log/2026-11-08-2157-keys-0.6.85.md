## 2. Cause (as confirmed)
The brief's guess was that the game reads the flag BEFORE OnKeyDown runs. The wiki says the opposite ("call this function from OnKeyDown
script handlers to consume only some keyboard events"): the flag set inside OnKeyDown counts for that key. So "the key after a handled
key is swallowed" does NOT happen out of combat (unless a handler errors, below). What the code does do:
1. In combat nothing sets the flag (every handler skipped SetPropagateKeyboardInput under InCombatLockdown, as it must). It stayed at
   what it was before the fight: false (keep every key) if the last key was one the window used (Delete or Ctrl+Z in the settings window,
   an arrow in the mover view), and, by the inference above, false if no key had been pressed since the window opened (the settings
   window and the mover key frame never set it on show). Then every key, movement and PRINTSCREEN included, stayed with the window for the
   whole fight. Old XayaUI_Options/Options.lua:1504-1512, XayaUI_Rules/Visual.lua:3192-3212. The mover view stays open in combat.
2. A Lua error in the settings window's key hook (RE.DeleteKey / RE.UndoKey) skipped the SetPropagateKeyboardInput line: the flag stayed
   as it was.
3. The settings window is AceGUI's Frame, recycled for other addons: its EnableKeyboard(true) and the hook (with the rule editor's
   Delete) stayed on it after release, so another addon's AceGUI window from the pool took keys and ran XayaUI's Delete.
4. Text boxes: a box keeps the keyboard until Escape (or its own Enter) clears it; a click elsewhere did not (by the inference above).
   The settings window's rule search box had no Enter at all, so after a search it held every key until Esc, which also wiped the search;
   the Notepad and the Calculator kept it after a click on the game world.
Which of these she hit is not known (was she in combat, was a box focused): open question.

## 4. Fix
- New core file XayaUI/KeyCatch.lua: `ns.KeyCatch(frame, handler)` (the flag rests at true: set on show, on setup, after any key not
  used, the next frame after a used key, and at PLAYER_REGEN_DISABLED before the lockdown; a used key is held for that key only;
  PRINTSCREEN never; in combat the flag is never touched and the handler is told inCombat; keyboard on only while shown and out of combat;
  `SetActive(false)` lets go; handler errors are reported and the key passes) and `ns.KeyFocusGuard(box, opts)` (SetAutoFocus(false);
  Escape clears unless the box has its own; Enter clears in a one-line box without its own; a click outside opts.within (default the box;
  the Calculator and the Notepad keep it for clicks inside their window, whose buttons work on the line) clears; the box or its window
  hiding clears; opts.onDone). `ns.KeyCatchList()` for the walkthrough.
- The three windows use ns.KeyCatch; the settings window switches it off in OnRelease and on again in EnsureChrome (c.owned).
- Every text box above calls ns.KeyFocusGuard; the settings search box's onDone stops its refocus-after-rebuild.
- The walkthrough reads the version pane through core's service list ("infoPane") and the rule search text through the new
  `ns.OptionsApi.TreeFilter` (Skin.lua), so Dev Assist does not reach into XayaUI_Options' names (harness boundary check).
