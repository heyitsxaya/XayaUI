## 1. Built into aura tracking
- **Glow.** It was already built in: the Buff / Aura reading's fallback 4, used only after a confirmed pairing. It was invisible,
  though. Every aura trigger's "In combat" line now says:
  - when its proc glow stands in ("present from its proc glow");
  - how many agreeing sightings are still needed;
  - or that a disagreement ruled it out.
  
  New `ns.ProcGlowInfo`. The rule-level summary counts a confirmed glow as readable.
- **Tier sets.**
  - **New table.** `XayaUI/SetBonusAuras.lua`, generated by the new `docs/reference/build_set_auras.py` from the game's own data
    (wago.tools ItemSetSpell, SpellEffect, SpellName, SkillLineAbility and TraitDefinition, build 12.1.5.70783), for the 41
    current sets in `docs/reference/spells/spells.json`.
  - **What it does.** An aura that only a set bonus can apply reads missing, in combat too, while that bonus is not active: too few
    pieces of the set (counted as by the Tier Set Pieces trigger), or the bonus is for another specialization. This is
    `ns.SetBonusOff`, step 0 of `ns.AuraPresence`, and the trigger's line says so.
  - **Coverage, a fact from the data.** The 41 current sets have 183 ItemSetSpell rows, 169 different bonus spells. Only 18 of those
    169 name what they trigger (EffectTriggerSpell); most
    are DUMMY or modifier effects handled by server scripts. For example, Retribution's 12.0 / 12.1 bonuses have no trigger in the
    data, so Divine Arbiter is not linked. So 18 auras are linked.
  - **Fail-safe.** An aura is linked only when nothing outside that set's own bonus chains applies it, and it is not a class or talent
    spell.
  - **Inferences.** That the trigger chain describes what the server does. That a buff already on you ends when the bonus goes
    (taking a piece off mid-buff is the one case that could read "missing" early).
- **The separate rows stay**, as the failsafe Xaya named.

## 2. Advanced Debugging
New `XayaUI/DebugRecord.lua`, after Console.lua in the toc.
- **Messages in their own frame.**
  - `ns.Print`, and XayaUI's own Lua errors, now go to chat, the XayaUI console window (Console.lua: its own movable frame that keeps
    collecting in combat), or both.
  - The default is the console window while Advanced Debugging is on, chat while it is off (unchanged).
  - The window opens when a message arrives, after combat if one arrives in combat.
  - Why the window and not a dedicated chat tab: a chat tab would change the player's chat windows (and the Chat Panel addon's), and
    the console window already existed with the right behaviour.
- **The record.**
  - **Contents:** while Advanced Debugging is on (and "Keep the debug record"):
    - every console line, which includes the existing rule snapshots at combat start and end and in-combat changes;
    - every message and XayaUI error;
    - combat start / end marks;
    - the combat engine's status at each combat end, collected silently through the new `ns.CaptureOutput`;
    - aura answer changes (Conditions.lua RecordAura, once per change, on both read paths);
    - glow sightings;
    - game-played sound set-up.
  - **Storage:** `CueRulesDB.debugRecord`, newest 3000 lines. The bug report adds the newest 1500; the SavedVariables file holds all
    of them.
- **Privacy.**
  - Rule names, spell IDs and XayaUI messages are kept.
  - No character name or realm.
  - Messages that can name another player use the new `ns.PrintPrivate`: shown, but never recorded, never put in `ns.logBuf` (which
    the bug report's "Last console lines", the console window's Copy and a reopened window read) and never collected. They are:
    - XayaUI_Chat "Ignoring <name>" (Ctrl + right-click);
    - XayaUI_Chat `/xui chat indent` (prints the first 40 characters of visible chat lines);
    - XayaUI_Chat `/xui chatprobe` top-left frames (up to 24 characters of each frame's text: player, target and party frames show
      names);
    - XayaUI_Bonus shared notes: "Saved <sender>'s note", "Ignoring shared notes from <sender>".
  - Scope (V4): every `ns.Print` / `ns.Log` / `Say` call in all addons was listed, and every name API (UnitName, GetUnitName,
    GetRealmName, Ambiguate, BNet, C_FriendList, guild) was traced to where its value goes. XayaUI_GameDump prints with its own `print`,
    so its lines never reach the record. The other hits print rule names, unit tokens (target, party1) or spell data.
  - The bug report's privacy line was corrected: it already showed rule names in console lines.
- **The game-data probe.** XayaUI_GameDump now provides the "gameDataProbe" service (Modules.lua contract; core never names it).
  Advanced Debugging switches it on. It switches it off again only if it was the one that started it; a probe the player started is
  left running.
- **Settings > Debugging:**
  - the Advanced Debugging description is rewritten;
  - new: XayaUI's messages (dropdown), Open the console window when a message arrives, Keep the debug record, Also run the game-data
    probe;
  - the record's size and where the file is;
  - Clear the debug record.

## Found in the review before committing (14:11 UTC)
- **Two settings could not be switched off.** `Ui().consoleAutoOpen = (not v) and false or nil` and the same for `debugProbe` always store
  nil (`true and false` is false, so `or nil` wins). Unticking "Open the console window when a message arrives" or "Also run the
  game-data probe" did nothing. `tests/lua_pitfalls_run.py` flagged both; now plain if / else.
- **The builder's merge could produce a wrong "missing" on a later build.** An aura linked from two bonuses of one set (for example a
  2-piece for one spec and a 4-piece for another) kept only the lower one's specs, so the other spec would read "for another
  specialization". Now: fewest pieces, every spec. In build 12.1.5.70783 each of the 18 auras has exactly one linking bonus and none
  is hero-tree-only, and the regenerated file is byte-identical, so nothing changes in game today.
- **The set-ID assumption, checked against the data.** `SetBonusOff` counts equipped items by the set ID `C_Item.GetItemInfo`
  returns. wago.tools ItemSet (same build) shows each of the 15 linked sets with its own items (5 per tier set, 2 or 3 for the crafted
  ones), no other set of the same name, and no item in a second set. So every piece maps to the one set ID in the table. That
  difficulties share one item ID per slot is an INFERENCE from this (a separate per-difficulty piece would show as a sixth item or a
  same-named set; there is none).
- `SetBonusOff` itself fails safe: item data still loading, or an unknown spec, gives "unknown", never "missing".
- **The aura record could break the aura read it watches (14:20 UTC, second commit).** `RecordAura` wrote the ID with `%d`. A rule
  whose aura ID is not a number (an import, a typo; `rule.buffID` and `buffAlt` are not converted first) made `string.format` raise
  inside `ns.BuffPresent`, but only with Advanced Debugging on. Now `%s` with `tostring(id)`; core 0.6.21, because 0.6.20 was
  already pushed on the branch. The full suite run on the first commit
  was stopped (18 groups had passed) and rerun on the second.
- **A privacy leak in the first version.** `ns.PrintPrivate` kept the message out of the record, but with messages going to the console
  window it still went into `ns.logBuf`, and the bug report copies the last 60 lines of that buffer. Fixed with a private flag that
  `ns.ConsoleMessage` honours (live window and tray only). The same sweep found the three other name-bearing messages listed above.
